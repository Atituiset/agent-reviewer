# AI 代码评审体系 MVP 实验报告

> 版本：2026-08-28 · 脱敏分享版（不含任何仓库地址、账号信息与密钥）
> 适用读者：想评估「在 AI Coding 流程中引入 AI 评审」可行性的工程团队
> 说明：本文涉及的试验仓以「仓 A / 仓 B」代称。仓 A 为自研 C++ 电信协议栈模拟器（数万行级）；仓 B 为某大型开源 C 项目（约 19k 源文件，千万行级量感）。CI 平台为 GitHub Actions，评审模型为 DeepSeek（经其 Anthropic 兼容端点接入，兼容 Claude Code 工具链）。

---

## 1. 背景与问题

AI Coding 工具把代码生成提速了一个数量级，但代码检视（code review）环节没有跟上，出现三个结构性问题：

1. **评审时机太晚**：主流 AI 评审工具在 PR 打开后才介入，commit/push 成本已沉没
2. **约束是建议性的**：写在项目说明文件里的评审规则遵守率约 80%，模型在认知负载下会"读了但不照做"——必须发生的评审需要机械门禁，而非提示词自觉
3. **评审结论不沉淀**：每次评审发现的缺陷模式、事故教训随会话结束消散，团队在同类型问题上反复踩坑

此外，我们的核心生产仓是**千万行级 C/C++ 嵌入式通信系统代码**（全局变量、函数指针、模板、虚函数密集），有一个突出的误报（FP）场景：指针在入口/分配处已判空，解引用处在 5~10 层函数调用之下未重复判空——AI 标为风险，开发者视为 FP。**不解决这类系统性 FP，评审工具会被团队静音。**

## 2. 调研结论（压缩版）

对业内 SDD（Spec-Driven Development）框架（OpenSpec、GitHub Spec Kit 等）、开源/商业 AI 评审工具（PR-Agent、CodeRabbit、Alibaba OCR、Anthropic 官方评审体系等）做了系统调研，收敛出五条核心共识：

1. 评审必须是流水线上的**机械门禁（gate）**，而非 prompt 里的建议
2. 评审者必须用**独立上下文**（fresh-context subagent），与实现者会话隔离
3. **误报治理 > 检出能力**——评审工具的死因不是漏报，是被团队静音
4. **过滤只能发生在独立验证段**——发现段不允许丢弃半信候选（Anthropic 内置评审 skill 的三态验证 CONFIRMED/PLAUSIBLE/REFUTED 是最佳实践）
5. **确定性工程 × Agent 混合**：文件选择、规则路由、定位、过滤交给确定性代码，LLM 只做判断（Alibaba OCR 用 benchmark 证明：同模型下 precision 33.9% vs 裸 agent 7.2%，token 仅 1/9）

## 3. MVP 设计

```
┌────────────────────────────────────────────────────────┐
│ 场景规则层（SKILL 格式，CWE 键控）                        │
│   13 个 CWE 场景 + 1 个通用基线；frontmatter 携带 glob    │
│   路由 → 确定性匹配，模型不参与「该跑哪些场景」的选择       │
├────────────────────────────────────────────────────────┤
│ 评审执行层                                               │
│   pre-commit 门禁（工件 hash 绑定 diff，评审后代码         │
│   动一个字节即失效）+ PR 阶段 CI 终审（GitHub Actions）    │
├────────────────────────────────────────────────────────┤
│ 输出层：canonical 工件（JSON）→ SARIF 2.1.0 投影          │
│   codeFlows 证据链 / reasoning 判断理由 / 评审轨迹归档     │
├────────────────────────────────────────────────────────┤
│ 飞轮层：TP/FP 人工标注 → quarantine → 人审 → 场景库/       │
│   团队记忆库演进（反馈资产归团队，不归模型厂商）            │
└────────────────────────────────────────────────────────┘
```

关键设计决策：

- **场景库用标准 SKILL.md 格式**：frontmatter 承载路由 glob 与元数据，正文为检测清单；路由由脚本生成注册表，单一数据源
- **门禁 fail-open + 豁免**：diff <20 行 / 纯文档豁免；门禁脚本自身故障放行（宁可漏拦不可误拦，否则团队会永久禁用它）
- **SARIF 是派生投影而非替代**：门禁语义（diff hash 绑定、verdict、ruling）留在私有工件；展示/交换走 SARIF（GitHub code scanning、VSCode SARIF Viewer 免费渲染）
- **证据链结构化**：每条 finding 必须带 `flow`（有序证据步骤）和 `reasoning`，评审纪律要求"无 file:line 证据不报、置信度 ≥80 才报、风格问题不报"

## 4. 试验设计与结果

### 4.1 机械链路验证（仓 B，播种缺陷）

向仓 B 播种 2 个已知模式缺陷（无界 strcpy 进栈缓冲、malloc 未判空），验证端到端机械行为：

| 验证点 | 结果 |
|---|---|
| 无工件直接 commit 被拦截，deny 附修正提示 | ✅ |
| 场景路由命中（C 文件 → 8 个 C 系场景 + 基线） | ✅ |
| fresh-context subagent 评审 | ✅ 2/2 播种命中 + **额外发现 1 个未播种真实问题**（导出函数无原型全树零调用） |
| 工件未解决被拦截 / ruling 后放行 | ✅ |
| 记忆治理（quarantine 不可召回 / 审核后可召回 / 无证据拒收） | ✅ |

### 4.2 CI 集成验证（仓 A + 仓 B，GitHub Actions）

可复用 workflow（`workflow_call`）：目标仓只需 10 行 caller + 3 个配置项（API key、模型端点、模型 ID）。评审模型 DeepSeek，**单次评审成本约 $1**（对比 Anthropic 托管服务 $15-25/次）。

- 仓 A 播种 3 缺陷：**3/3 检出，零误报**
- 仓 B 播种 3 缺陷：**3/3 检出 + 2 条真实增量发现**（死代码；`strlen(banner)>64` 守卫恒为假——模型推演了 snprintf 的长度上限），零误报
- SARIF 上传 code scanning：告警含判断理由 + 证据链全文，alert 详情 Show paths 可逐步跳转

过程中的 6 轮真实排障（对自建者有参考价值）：OIDC 权限缺失 → Claude App 安装要求（改传 GITHUB_TOKEN 绕过）→ action 重置工作区清掉工具仓（工件改落 /tmp）→ 默认工具白名单拒写（19 次 deny，改显式放行）→ 默认分支引用错误 → SARIF schema 细节（codeFlows 的 message 必须放在 location 对象内）。

### 4.3 三模式对比（仓 A，两套试验件）

模式定义：**模式 1** = 纯场景库；**模式 2** = +codegraph（tree-sitter 调用图，PR 时秒级索引）；**模式 3** = 模式 2 + navmap（libclang 语义导航图：消息分发表/状态机表/全局变量读写清单，nightly 预计算，PR 时零时延消费）。

**试验件 A（abort 兜底契约，2 层直连）**：三个模式均未产生 FP——契约显式可见时基线模型自足。意外：试验件无意埋入的真缺陷（strcpy 无界进 64 字节）被三模式全部稳定命中。

**试验件 B（入口判空 → 函数指针表分发 → 5 层转发 → 深处解引用）**——核心仓真实 FP 场景的微缩复刻：

| 模式 | cwe-476 结果 | 评价 |
|---|---|---|
| 模式 1 | **报了（FP 复现成功）** | 无法跟踪表分发 |
| 模式 2 | **抑制** | codegraph 链回溯生效（实测调用 29 次） |
| 模式 3 | **报了但理由质变**：「判空仅在入口单一路径，引擎入口是公开的，直接调用即绕过判空」 | 不是 FP，是**比 FP 更深的真实发现** |

三模式还共同命中一个非设计播种的真实缺陷（零长缓冲区 1 字节越界读）。

### 4.4 关键认知

1. **系统性 FP 可以可靠复现，但规模是差异化的前提**：契约可见（同文件、2-3 跳、abort 兜底）时，当前档位的模型无需调用图也能理解；FP 在「表分发 + 跨文件 + 长链」同时出现时才必然产生——这正是千万行级仓的常态
2. **两层索引架构有效**：codegraph（通用调用图，tree-sitter，无构建依赖）打底 + navmap（语义导航图，libclang，nightly 预计算）补函数指针/全局变量/状态机缺口
3. **判空契约必须显式化**：「上游已判空」的 FP 标注应提炼为仓库级「判空契约」规则资产（经人审入库），并可用分发表机械校验契约覆盖率——从「事后逐条标 FP」升级为「规则级豁免」

## 6. 经验与教训

1. **评审左移的价值是结构性的**：commit 前拦截的成本是分钟级，PR 后修复是完整循环
2. **误报治理三件套第一天就要在**：显式不报清单、独立验证段、可量化的回放基线（golden case 回放）
3. **小仓试验会高估基线模型**：模式差异在足够小的代码上会被模型的局部推理能力掩盖——试验件设计必须让证据超出局部可见范围（函数指针 + 跨文件 + 长链）
4. **CI 集成的坑集中在「runner 是黑盒」**：action 会重置工作区、默认工具白名单、OIDC/App token 两套体系——全部要靠日志逐层排障，建议预留 3-5 轮调试预算
5. **SARIF 是回报最高的标准化选择**：code scanning 展示、Show paths、VSCode 渲染全部免费，但它是交换格式不是人读界面——人读结论要么进告警 message 全文，要么进 PR 评论（可选）
6. **反馈资产的归属决定飞轮是否成立**：TP/FP 如果归模型厂商，团队永远在用别人的评审器；归自己（经人审入规则库/记忆库），系统才会随团队越用越准

## 7. 演进路线（摘要）

- **生产可用（2-4 周）**：三态验证进评审纪律；golden case 回放基线；结构化输出通道替代文件写入；按 PR 规模分档控成本；评外部 PR 的安全加固（配置从 base 恢复、防注入、输出脱敏）
- **质量收敛（1-2 月）**：告警生命周期（fixed 跟踪、去重排序、re-review 收敛）；per-scenario precision 月报淘汰低效场景
- **规模化（2-3 月）**：飞轮全量生产化（失效引擎、判空契约库）；多仓推广 kit；度量看板

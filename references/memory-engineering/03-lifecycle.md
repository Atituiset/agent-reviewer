# 03 生命周期与失效管理

对 ANDM 失效引擎最重要的一份参考。

## 3.1 写入决策树（前置过滤）

```
个人/业务意义? No → IGNORE
重复? Yes → MERGE/UPDATE
含新事实? Yes → STORE as SEMANTIC
值得记忆? Yes → STORE as EPISODIC
否则 → IGNORE
```

应忽略的清单：寒暄、纯功能指令、**临时状态**（"我现在在车上"——但"通勤方式=开车"应存）、相似度 >0.9 的重复、**被纠正后的错误信息**。

ANDM 研发语境的对应区分：「这个 PR 还没合」是临时状态，「这个模块的 owner 是 X」是稳定事实；**agent 一度误判、后被 review 纠正的结论绝不能成为团队记忆**（§10.3）。

## 3.2 时间衰减（Ebbinghaus 式指数衰减，按类型分档）

```
importance(t) = importance_initial × e^(-λ×t)
λ: Episodic = 0.01（30 天 → 74%）
   Semantic = 0.001（→ 97%）
   Procedural = 0.0001（几乎不衰减）
```

- 衰减锚定**上次被访问时间**（命中即重置），不是创建时间
- `importance(t) < threshold` 触发**硬遗忘**：归档冷存储、移出热索引、保留可恢复标记
- 越抽象、越规则化的记忆衰减越慢

ANDM 映射：session 级事实用快衰减，模块级规约/架构决策用慢衰减或不衰减；但 **ANDM 的主失效信号不是时间而是代码变更**——时间衰减降级为兜底（长期无人召回的条目自然沉底），§10.4。

## 3.3 重复合并与冲突解决（伪代码级）

```
candidates = filter(cosine_sim > 0.85)
无候选 → 直接存储
有候选且矛盾 → 比较 confidence：新高则 update 覆盖；否则 add_alternative（保留两者，标记冲突）
有候选且互补 → enrich 合并 + update_timestamp + increment_mention_count
```

- 冲突检测由 LLM 判断矛盾；裁决不了就**双版本并存 + 冲突标记**，不强行二选一

ANDM 增强（§10.3）：冲突检测除语义矛盾外增加确定性信号——**两条目绑定同一代码区域但结论相反**；裁决依据用「绑定代码版本新旧 + 审核人权限」替代纯 confidence；双版本条目注入时必须同时标注冲突。

## 3.4 pinned 与软删除（治理权边界）

- `pinned` 条目：λ=0、跳过去重合并、跳过硬遗忘、只被 consolidation 引用不被改写
- 原则：**自动系统只能「降级/归档」，只有用户能「删除」**；删除需二次确认、默认软删除可恢复

ANDM 对应（§10.4）：团队 lead 确认的架构决策类条目对自动失效免疫——失效引擎最高权限是「降级/移出召回池」，pinned 条目只能「标记待人工复核」；物理删除只能由人执行。

## 3.5 记忆进化/升级的触发条件

「同一主题出现 ≥ 3 次且时间跨度 ≥ 7 天」→ 多条 episodic 提炼为一条 semantic 结构化条目。数量阈值 + 时间跨度双条件，防止单次集中事件误判为规律。

ANDM 映射（§10.4）：触发轴换成「同一模块的同类 review 意见出现 ≥ N 次且跨度 ≥ 7 天」→ 蒸馏为模块级规约条目。

## 3.6 反馈驱动退化

`success_rate` 依赖「执行 → 验证 → 回写」闭环；成功率下降触发重学/降级/淘汰。

ANDM 对应（§10.2）：条目召回后埋点回收信号——被采纳 vs 被忽略 vs 被标记误导；命中率低于阈值触发降级重审。这是「误导性条目率」度量的数据源头。

AI 代码评审 MVP：从代码修改到评审告警的全链路

场景库驱动 · 调用图增强 · SARIF 标准化 · 反馈飞轮

⏱ 30 秒速览
  • 问题：AI 写码提速后，评审没跟上——PR 后评审成本已沉没、规则靠 prompt 自觉、结论不沉淀；千万行级 C/C++ 仓还有「上游已判空、深处解引用」的系统性误报。
  • 做法：CWE 场景库（SKILL 格式 + 确定性路由）+ commit 前机械门禁 + PR 端 CI 评审（DeepSeek）+ 调用图证据链回溯 + SARIF 标准化输出 + TP/FP 反馈飞轮。
  • 结果：播种缺陷 12/12 检出、0 误报、6+ 条真实增量发现；单次评审 ~$1（托管服务 $15–25）；三模式实验证明调用图能抑制表驱动误报、语义导航图能发现契约级问题。
  • 关键差异：反馈资产归团队（TP/FP 经人审进规则库），评审左移到 commit 前，成本差 15–25 倍。

CI 实现

CI 实现：一个仓生产，所有仓继承

评审逻辑集中在 agent-reviewer 仓的可复用 workflow；目标仓只放一个 10 行 caller，评审升级时目标仓零改动。

目标仓 caller · .github/workflows/ai-review.yml（全部 10 行）
name: ai-review
on:
  pull_request: [opened, synchronize]
permissions:
  contents: read
  security-events: write
  id-token: write
  pull-requests: write
jobs:
  review:
    uses: <org>/agent-reviewer/.github/workflows/ai-review-reusable.yml@mvp
    secrets: inherit

uses = 引用可复用 workflow（函数调用）；secrets: inherit = 把目标仓的模型配置（DeepSeek key / 端点 / 模型 ID）传给被调用方；评审逻辑更新时目标仓零改动。

发给模型的 prompt（按模式组装）

模式 2 实际拼装的评审指令：场景路由、清单评审、判空链回溯、工件 schema 全部写死在指令里。

你是 task-reviewer。读取 /tmp/pr.diff 与 .reviewer/rules/registry.json：
1. 用 .reviewer/scripts/_lib.py scenarios-for 对 diff 触及的每个文件做场景路由
2. 对每个命中场景，读 .reviewer/rules/scenarios/<key>/SKILL.md 清单逐项评审
3. 纪律：只报有 file:line 证据的具体缺陷；置信度 ≥80 才报；风格问题不报
3.5 跨函数判空链回溯（cwe-476 类候选必做）：上报「解引用未判空」前，用 codegraph CLI
   （codegraph callers <fn> / callees <fn>）沿调用链回溯 ≤10 跳：
   - 上游找到判空（同一指针）→ 不报（FP 证伪，可在 reasoning 记录证伪链）
   - 链在函数指针/虚函数处中断 → 保留但 reasoning 必须标注「链中断于 X，静态不可判定」
   - 未做链回溯的跨函数判空 finding 不报
4. 将结果写为 .review/review-artifact.json，schema：{diff_hash, verdict, findings:[{file,line,
   severity,scenario,summary,detail,confidence,flow:[证据链],reasoning}]}

CORE VALUE

核心价值：同一份代码，三种命运

评审工具的死因不是漏报，是被团队静音——而系统性误报只能靠索引层治理。

①

LLM 评审的天然边界

探查半径是 grep / Read 级的 1–2 跳；「上游已判空、5–10 跳外解引用」超出半径 → 只能按疑似上报 → FP。

②

codegraph 把「猜」变成「查」

判空链回溯（callers BFS ≤10 跳）让「上游有没有判空」从推测变成可查证——找到判空才证伪，断链只能 PLAUSIBLE。

③

navmap 补上静态盲区

函数指针表 / 状态机 / 全局变量是调用图的断链点——语义导航图把「不确定目标」展开为 handler 集合做保守近似，契约从「宣称」变「可校验」。

# C/C++ 高误报场景清单：静态分析传统误区与场景库消化策略

> 日期：2026-08-28
> 用途：场景库 V1 扩容的设计输入。面向千万行级 C/C++ 嵌入式仓，梳理传统静态分析（SA）与 LLM 评审都容易误报的场景，并给出在我们的体系（场景 SKILL / 索引层 / exemption_pattern 契约 / 回放基线）中的消化策略
> 定位：这不是缺陷清单，是「误报治理地图」——每一条都要回答：SA 为什么报、LLM 会不会跟着报、我们怎么不冤枉它

---

## 0. 误报治理总原则

1. **误报三来源**：跨文件契约（判空/锁/所有权在上游）、惯用法不识（goto-err/FAM/无锁队列）、配置盲区（#ifdef/产品形态/宏生成）
2. **LLM vs SA 的能力差**：LLM 对惯用法理解显著好于传统 SA（能读懂 goto-err、FAM、abort 兜底），但**跨文件契约场景两者同样失效**——这正是索引层（codegraph/navmap）和契约注入（exemption_pattern）的主场
3. **消化策略四件套**（每条场景标注其一或组合）：
   - **【契约】**exemption_pattern 入库（人审后注入评审）
   - **【索引】**codegraph 链回溯 / navmap 表查证
   - **【不报】**场景 SKILL 显式不报条款（附判定条件，禁止无差别豁免）
   - **【回放】**golden case 负例校准（必须含「故意的 X」正例防误杀）

## 第一篇：C 语言高误报场景

### 1. 契约型指针安全

| # | 场景 | SA 误报机理 | LLM 预判 | 消化 |
|---|---|---|---|---|
| C1 | 上游判空、深处解引用（5-10 跳，可跨文件/经分发表） | 过程间分析深度不足，按本地不可证报空指针 | 同 SA，探查半径 1-2 跳 | 【索引】链回溯 +【契约】判空契约 |
| C2 | 返回值不检查：错误码在更上层集中处理 / allocator 失败即 abort | 报 unchecked return | abort 兜底可见时能懂；集中处理跨文件时同样报 | 【契约】错误处理约定入库 |
| C3 | 断言守护（PLM_ASSERT 类自定义宏）的解引用 | release 语义下认为路径可达 | 标准 assert 能懂，自定义宏需要说明 | 【不报】断言宏名单注入场景规则 |
| C4 | `goto err` 集中清理 / arena-pool 统一回收 / 启动期永驻单例 | 路径合并报泄漏、double-free | **LLM 较强的领域**，惯用法大多能懂 | 【回放】正例防误杀为主 |
| C5 | 所有权经出参/回调转移（"调用方负责释放"注释约定） | 不知道转移契约报泄漏/UAF | 同文件注释可见时能懂，跨文件断 | 【契约】所有权约定入库 |
| C21 | **全局变量启动期初始化**：`g_xxx` 定义时为 NULL，系统启动阶段 malloc 赋值，业务期 N 层函数直接解引用不判空 | 按定义值 NULL 推「可能空指针解引用」全报 | **电信仓超高频**：生命周期跨编译单元且赋值发生在 init 阶段，LLM 与 SA 同样全报 | 【契约】`startup_init_contract`（启动初始化契约）+【索引】navmap 全局变量读写清单验证「存在启动期写点」——**该类契约可部分机械验证**（写点存在性、写点位于 init 类函数） |

### 2. 边界与长度（CWE-119/125/787）

| # | 场景 | SA 误报机理 | LLM 预判 | 消化 |
|---|---|---|---|---|
| C6 | 柔性数组成员 `uint8_t data[]` / 变长结构体按 len 分配 | 按声明大小报越界 | 惯用法大多能懂；len 在另一层头里时断 | 【不报】FAM 模式 +【索引】len 来源回溯 |
| C7 | 容量 vs 有效长度：`char buf[64]` 约定只用前 32（协议定长字段） | 按容量判安全或按约定报越界，两头错 | 注释写明约定时不报，无注释时按保守报 | 【契约】容量约定写入场景/记忆 |
| C8 | 协议解析步进偏移：每步边界在解析入口统一校验 | 逐步报越界 | 单文件内能跟上，跨文件断 | 【索引】校验点回溯 |
| C9 | memcpy/长度字段在入口已验证，深层不再校验 | 报未验证长度 | 与 C1 同构 | 【索引】+【契约】 |
| C10 | `strcpy/sprintf` 等"非受限 API"：长度已被固定格式/已知上限约束 | API 黑名单式全报 | 会报但可给出反证要求 | 【不报】须给出「长度上界证据」才可报，否则不报 |

### 3. 整数与序号语义（CWE-190）

| # | 场景 | SA 误报机理 | LLM 预判 | 消化 |
|---|---|---|---|---|
| C11 | 有界域理论溢出：len 来自 16 位协议字段、数组有宏上限 | 污点分析报溢出 | 报「潜在溢出」倾向高 | SKILL 已要求「溢出后的具体危害路径」，无路径不报【不报】 |
| C12 | 有意的回绕/模运算：协议序号空间、时间戳差值 `int16_t(a-b)`、哈希 | 几乎必报 | 需要设计注释才能识别 intended wrap | 【契约】回绕语义声明 +【回放】必须含「故意的回绕」正例（rlc_um 是真 bug 的反证——不能一刀切豁免） |

### 4. 并发与执行模型（CWE-362）

| # | 场景 | SA 误报机理 | LLM 预判 | 消化 |
|---|---|---|---|---|
| C13 | 单线程事件循环/协作式调度下的共享变量「未持锁」 | 默认抢占模型全报 | **LLM 较强**：能识别事件循环（我们 bs_node.cpp 实测正确） | SKILL 要求「先判定执行模型再下结论」【不报】 |
| C14 | 锁在另一层："caller must hold mtx" 约定 | 锁作用域不可见 | 同文件注释可懂，跨文件断 | 【契约】锁契约（与判空契约同构） |
| C15 | SPSC 无锁环形缓冲 + 内存屏障手写同步 | 报 data race | 几乎必误报 | 【不报】SPSC 无锁队列模式（附判定条件：单生产单消费可证） |

### 5. 状态机与枚举闭合

| # | 场景 | SA 误报机理 | LLM 预判 | 消化 |
|---|---|---|---|---|
| C16 | switch 枚举全集闭合、故意无 default | 报缺 default | 也常报「缺缺省分支」 | 【不报】枚举可证全覆盖不报，但要求列出覆盖证明 |
| C17 | 状态机不变量：「该状态下该值不可能」 | 不知状态约束报非法路径 | 猜测式误报 | 【索引】navmap 状态机表注入，迁移合法性查表 |

### 6. 构建配置与代码形态

| # | 场景 | SA 误报机理 | LLM 预判 | 消化 |
|---|---|---|---|---|
| C18 | `#ifdef` 多产品形态下的「死代码/未使用函数」 | 单配置视角报未使用 | dead-code finding 会误伤（我们 default 基线即有此风险） | 配置矩阵上下文（compdb -D）+【不报】多配置仓需产品形态注入 |

| C20 | 宏拼接的初始化（`INIT_FOO(a)` 内部含校验） | 报缺校验 | 需要宏展开上下文 | 【索引】compdb 参数下的宏展开（navmap 已带正确 -D） |

## 第二篇：C++ 高误报场景

### 7. RAII 与智能指针

| # | 场景 | SA 误报机理 | LLM 预判 | 消化 |
|---|---|---|---|---|
| P1 | `unique_ptr` move 后源指针「再使用」——约定不再用但注释/断言守护 | 报 use-after-move | 能懂 move 语义，约定在注释时懂 | 【回放】正例即可，误报率低 |
| P2 | 自定义 handle 包装类（fd/SOCKET/句柄析构释放）：「成员未在析构释放」 | 不认识自定义释放逻辑报泄漏 | 析构可见时能懂；跨文件 handle 类断 | 【索引】析构函数定义回溯 |
| P3 | 成员是容器/智能指针却报「析构未释放成员」 | 不理解自动释放 | 一般不会报，偶发过报 | 【回放】负例即可 |
| P4 | 异常路径「资源泄漏」：栈展开 RAII 自动清理 | 不理解 RAII 报泄漏 | **常见误报**：LLM 对「构造即入容器」惯用法大多能懂，对自定义 guard 类跨文件时断 | 【不报】RAII 类型名单 +【索引】 |
| P5 | `shared_ptr` 循环引用「泄漏」实为缓存/观察者设计 | 报潜在泄漏 | 会提 but 置信度应低 | 【契约】所有权设计说明入库 |

### 8. 虚函数与继承

| P7 | 虚函数未标 override/final | 风格化全报 | 属「明确不报的样式问题」 | 【不报】归入风格类（评审纪律已有） |

### 9. 模板与实例化

## 第三篇：C/C++ 混合编程高误报场景

> 电信仓的典型形态：C 协议栈/驱动 + C++ 框架/应用，大量交互发生在语言边界上。
> 混合场景的误报有一个独有来源——**分析器（和模型）往往以单语言语义看双语言世界**：
> 在 C++ TU 里看不到 C 侧调用，在 C TU 里看不到 C++ 生命周期。判空契约、所有权、
> 布局约定一旦跨越语言边界，两侧的工具都只剩一半证据。

### 13. extern "C" 边界与跨语言调用

| # | 场景 | SA 误报机理 | LLM 预判 | 消化 |
|---|---|---|---|---|
| M1 | C++ 函数 `extern "C"` 导出给 C 调用方——C++ TU 内「零调用死代码」 | 单语言视角查不到 C 侧调用 | **高发且与我们直接相关**：default 基线的 dead-code finding 会误伤导出符号 | 【不报】`extern "C"` 导出符号不以「本 TU 无调用」判死代码，需全仓跨语言调用证据（codegraph 跨语言边） |
| M2 | C 侧经函数指针回调 C++ 函数（注册给 C API） | 链接/类型检查报不匹配、调用图断 | 回调注册跨文件跨语言，几乎必断 | 【索引】navmap 注册式分发点（libclang 同前端，C/C++ 通吃）+ codegraph |
| M3 | **判空契约跨语言边界**：C 入口判空 → C++ 引擎深处解引用（电信仓最高频形态） | 两侧分析器各看一半 | 同 M1 高发——这正是核心仓判空契约的主形态 | 【索引】跨语言链回溯（codegraph 双语法解析天然支持）+【契约】契约声明不区分语言 |
| M4 | C++ 异常穿越 C 帧（调用栈中间有 C 函数） | 报 UB；但团队约定「异常不跨边界」时反向误报（报缺少异常安全） | 多半不懂嵌入式无异常约定 | 【契约】「本仓禁用异常/异常不出模块」声明入库；跨边界 throw 才报 |
| M5 | setjmp/longjmp 跳过 C++ 析构 | 报资源泄漏/析构缺失 | 嵌入式禁用 longjmp 约定常见 | 【契约】禁用声明；混用才报 |

### 14. 共享头文件与 ABI 布局

| # | 场景 | SA 误报机理 | LLM 预判 | 消化 |
|---|---|---|---|---|
| M6 | 同一头文件被 .c/.cpp 双编译：结构体 packing/对齐/位域布局「不一致」 | 按单一语言规则报不一致 | 位域跨语言是老坑，易过报也易漏报 | 【索引】navmap 全局变量布局清单（已带布局）做双侧比对 |
| M7 | enum 底层类型差异：C++ scoped enum 固定底层类型 vs C enum 编译器自选 | 报跨边界大小不匹配 | 跨边界传 enum 才真有问题，否则过报 | 【不报】不跨 extern "C" 边界不传 enum 时不报 |
| M8 | C 侧用 C++ 关键字作标识符（`class`/`new`/`template` 变量名）——C 合法 C++ 非法 | 共享头文件在 C++ TU 报编译错 | 真实问题（报得对）但常被当误报忽略 | 保留上报（这是真兼容性问题），severity 降为 important |
| M9 | `bool`/`BOOL`/`int` 真假值三体系混用（历史 C 代码自定义 BOOL） | 报类型不一致 | 跨边界 ABI 大小一致时不算缺陷 | 【不报】同尺寸布尔约定不报；尺寸不同才报 |

### 15. 内存管理跨语言

| # | 场景 | SA 误报机理 | LLM 预判 | 消化 |
|---|---|---|---|---|
| M10 | `malloc` 分配 C++ 用 `free` 释放（正确配对）却被报「应用 delete」 | 语言偏好式全报 | 配对正确时被教桩式报 | 【不报】malloc/free、new/delete 按配对判定，不按语言判定 |
| M11 | C API 约定的「C 分配、C++ 侧释放」（库契约规定用其 free 函数） | 报所有权混乱 | 库契约不可见时必报 | 【契约】库分配/释放契约入库 |
| M12 | placement new 在 C 侧分配的 buffer 上（嵌入式无堆/静态池设计） | 报生命周期/对齐问题 | 静态池模式常见，多误报 | 【契约】内存池设计说明（与 P20 同族） |
| M13 | 非平凡 C++ 对象经 `realloc` 搬迁 | 报 UB | 多数能识别为真问题 | 保留上报（真 UB 高发区） |

### 16. 静态初始化与嵌入式运行时

| # | 场景 | SA 误报机理 | LLM 预判 | 消化 |
|---|---|---|---|---|
| M14 | C 代码在 C++ 静态对象构造前使用它（init order / 手动 .init_array） | 报「使用未初始化对象」 | 启动顺序问题在嵌入式真实存在，但静态误报率也高 | 【契约】启动顺序说明；「main 前无 C 调用」类声明入库 |
| M15 | 无标准运行时环境（裸机/RTOS）下的「缺少 new/异常/rtTI 支持」报法 | 按 hosted 环境报 | hosted/freestanding 不分必误报 | 【契约】freestanding 声明入库（影响 new/异常/STL 全部判定） |

### 17. ODR 与链接语义差异

| # | 场景 | SA 误报机理 | LLM 预判 | 消化 |
|---|---|---|---|---|
| M16 | C inline 与 C++ inline 语义差异导致的「重复定义/缺失定义」 | 单语言规则报链接问题 | 共享头 inline 函数高发 | 【不报】双编译头文件中的 inline/static inline 模式不报，除非有真实 ODR 证据 |
| M17 | C 的 `restrict` 在共享头中（C++ 无此关键字） | 按 C++ 报语法错 | 宏封装惯例（`#ifdef __cplusplus`）能懂，裸写报错 | 【不报】`#ifdef __cplusplus` 包裹的 restrict 宏模式不报 |

## 混合编程篇与前面两篇的关系

- **M3 是 C1（跨函数判空契约）在混合仓的真实主形态**——前面设计的 codegraph 链回溯和 exemption_pattern 不需要为混合场景另起炉灶，只需确认「跨语言边」在索引里存在（codegraph 的 tree-sitter 对 C/C++ 分别提取、统一建边，实测已覆盖；navmap 的 libclang 同前端天然双语言）
- **M1 是对我们 default 基线「死代码」场景的直接修订项**——extern "C" 导出 + 注册表驱动是电信仓入口函数的主流形态，判死代码必须查跨语言调用证据，否则系统性误伤
- **M6 与 navmap 全局变量布局清单天然衔接**——navmap `globalvar` 提取已带布局信息，混合仓里它是「结构体布局双侧一致性」的现成证据源

## 第四篇：IPC 与进程/任务间通信高误报场景

> 电信仓的内存和消息大量跨进程/任务流动：内存按 PID 申请、消息经队列传递、
> handler 在对端进程注册。这类场景的误报根源比跨文件更硬——**所有权、判空、
> 生命周期的证据链在进程边界上物理断开**，任何静态工具（含 codegraph）都到不了
> 对端。消化原则因此调整：能登记成「API 契约表」的走机械校验（navmap 注册 API
> 名单），登记不了的走「系统级契约声明 + 人审」，不指望工具自动闭合。

### 18. IPC 内存与消息生命周期

| # | 场景 | SA 误报机理 | LLM 预判 | 消化 |
|---|---|---|---|---|
| I1 | **按 PID 申请、释放归开辟方**：`buf = ipc_alloc(PID_X, size)` 后本进程不释放——内存所有权归 IPC 框架/内存管理方统一回收 | 一切泄漏分析全报 | **必报**（cwe-401 直接命中）且完全错误 | 【契约】`ipc_ownership_contract`：「API X 分配的内存归 Y 释放」入库；alloc/free 配对 API 名单进场景规则 |
| I2 | 消息 buffer 发送后归框架：`ipc_send()` 语义 = 所有权转移给框架/对端 | 报发送后未释放 | send 语义不可见时报 | 【契约】所有权转移 API 名单（`ipc_send` 类）入库；「传给名单内 API 的 buffer 不再追泄漏」 |
| I3 | 共享内存池（SMP）/静态池：固定地址固定布局，无释放概念 | 报泄漏/未初始化/越界 | 静态池模式常见误报 | 【契约】内存池声明（与 P20/M12 同族，IPC 场景主形态） |
| I4 | 引用计数消息：`msg_ref++/unref--`，释放由计数归零驱动 | 报未释放/double-free | 计数宏跨文件时断 | 【契约】refcount API 名单；计数型内存不报路径泄漏，只报计数不配平 |
| I5 | 错误路径上「框架统一回收 + 业务自判释放」并存 | 路径合并报 double-free | 可能误报也可能真报 | 【回放】框架回收路径标注后按框架路径判定；无标注按业务路径判定 |

### 19. IPC 同步、分发与状态

| # | 场景 | SA 误报机理 | LLM 预判 | 消化 |
|---|---|---|---|---|
| I6 | 按 PID/TID 的消息路由表：handler 在**对端进程**注册，本地「表项 handler 未定义/零调用」；含**一维/多维函数指针数组表**（`tbl[N]` / `tbl[N][M]`，call hierarchy 类工具完全不可达） | 单进程视角报未定义/死代码；表驱动调用链对 call hierarchy 与 codegraph 均断 | **与 M1 同源的 IPC 版**：注册 handler 是入口函数主流形态，死代码判定必须认注册点 | 【索引】navmap 注册式分发点 + 分发表提取（已支持裸一维/多维函数指针数组，msg_id=复合下标）——产物即「注册点 = 使用证据」与断链续链依据 |
| I7 | handler 被对端经 IPC 调用的判空契约：对端保证消息非空/字段有效 | 工具链内完全不可验证 | 必报且无法自证 | 【契约】**系统级契约声明**：「进程 P 发给进程 Q 的消息 M 保证字段 F 有效」，人审 + 协议文档锚点，不做机械验证承诺 |
| I8 | 跨进程信号量/消息队列的阻塞等待 | 报死锁/挂起/未配对 | 阻塞语义可见时能懂，跨进程配对不可见时报 | 【契约】信号量/队列配对声明入库 |
| I9 | 「发送后等响应」的跨进程状态机：本地看是状态悬挂/无超时 | 报状态机不完整/悬挂 | 协议状态机不可见时报 | 【契约】IPC 状态机声明；超时由框架统一管理的声明 |
| I10 | 定时器/看门狗回调上下文由框架保证有效（「未判空/未使用返回值」） | 框架约定不可见 | 定时器回调是电信仓高发区 | 【契约】回调上下文约定入库 |

## IPC 篇与工具体系的映射（关键）

1. **I1/I2 是你们点名场景的落地**：消化不靠 LLM 更聪明，而靠把「`ipc_alloc(PID)` 申请归开辟方释放」登记成**契约表**——审查时注入「该 API 的内存归 Y 释放」，cwe-401 类 finding 直接从根上不产生。这份契约表就是 navmap `register_apis` / `suggest-apis` 的设计本意：先 `suggest-apis` 粗提候选 → 人审 → 入 `navmap.toml`，提取产物即契约证据
2. **死代码判定第三次被点名**（M1 extern "C" → I6 IPC 注册 handler）：电信仓入口函数的三大形态——extern "C" 导出、注册表、IPC 对端调用——全是「本地零调用」，default 基线的死代码场景必须改为「无跨语言/注册点/IPC 证据才可报」，这是混合仓死代码判定的**前置修复项**
3. **跨进程契约（I7）是治理边界**：工具链内不可验证的，诚实走「契约声明 + 人审 + 协议文档锚点」，不承诺机械验证——这与 exemption_pattern 的设计一致（验证不了的留人审通道）

## 附 B：exemption_pattern 契约类型（ANDM 侧新增 kind 的建议）

| 契约类型 | 内容形态 | 可验证方式 |
|---|---|---|
| `null_guard_contract` | 「模块 X 在入口/分配处判空，下游不重复判」 | codegraph 链回溯 + navmap 表覆盖率 |
| `lock_contract` | 「函数 F 调用方须持锁 M」 | codegraph 调用点锁检测（启发式） |
| `ownership_contract` | 「函数 F 出参所有权归调用方 / 归 pool」 | 释放点存在性检查 |
| `capacity_contract` | 「buf[N] 约定只用前 M 字节」 | 静态范围比对（部分可验证） |
| `error_handling_contract` | 「错误码由上层 H 集中处理」 | 透传链闭合检查 |
| `wrap_semantics` | 「该序号为有意回绕模运算」 | 设计注释 + 不可机械验证（人审兜底） |
| `execution_model` | 「模块 X 为单线程事件循环」 | 无 std::thread/创建点检查（navmap 全局量联动） |
| `config_matrix` | 「函数 F 在产品形态 Y 下使用」 | compdb -D / 构建配置比对 |
| `abi_boundary` | 「头文件 H 为 C/C++ 双编译，布局约定 X」 | navmap 布局清单双侧比对 |
| `exception_policy` | 「本仓禁用异常 / 异常不出模块」 | 跨边界 throw 存在性检查 |
| `freestanding` | 「本仓无 hosted 运行时（裸机/RTOS）」 | 影响 new/异常/STL 判定，人审兜底 |
| `ipc_ownership_contract` | 「API X 分配的内存归 Y（框架/对端/PID owner）释放」 | alloc/free API 配对表（navmap register_apis 提取 + 人审） |
| `ipc_transfer_api` | 「API X（ipc_send 类）接管 buffer 所有权」 | 名单匹配（navmap 注册点产物） |
| `ipc_message_contract` | 「进程 P→Q 的消息 M 保证字段 F 有效」 | 跨进程不可机械验证，人审 + 协议文档锚点 |
| `dynamic_symbol` | 「符号 S 由热补丁/动态加载解析」 | 声明 + 符号表/patch 描述锚点 |
| `startup_init_contract` | 「全局量 g_xxx 于系统启动期由 init 类函数分配初始化，业务期按非空使用」 | navmap 全局变量读写清单：验证写点存在性 + 写点位于 init/startup 类函数；LLM 评审时 codegraph 查写点复核 |

每类契约依然是 **quarantine → MDE 审核 → active** 的治理流，且优先选「可机械验证」的类型——验证不了的（如 wrap_semantics）永远留人审通道。
